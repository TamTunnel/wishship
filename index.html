WishShip

The vote-to-ship loop for app builders. Users submit feature requests and vote on them; a coding agent implements the winners and opens verified pull requests.

Repository on GitHub · Apache-2.0 · TypeScript / Node · Fastify + React + Postgres

How the loop works

  1. Board. A maintainer installs the WishShip GitHub App on a repo. Users sign in with GitHub, submit wishes, and upvote them. Votes are public: who voted for what is visible.
  2. Cycle. Weekly (configurable), the cycle closes and the top-voted wish above the threshold is proposed. No winner below threshold: nothing is proposed.
  3. Approval — human gate 1. The maintainer approves or rejects the winner. No approval, no agent run, no money spent. A rejected winner returns to open; it never auto-advances to the runner-up.
  4. Agent run. A coding-agent CLI runs in a fresh temp worktree with a scrubbed environment (no GitHub token, no npm auth, no service credentials). The agent never pushes: the PR branch is service-created.
  5. Verification — the moat. Deterministic checks run on a clean checkout with the diff applied: the repo's own tests, lint, typecheck, secret scan, diff-size limit, churn check, dependency rules, and new-network-call flagging. The result is a tier, not a boolean: VERIFIED, PARTIAL, or BLOCKED. Only VERIFIED or PARTIAL reports open a PR.
  6. Draft PR — human gate 2. The PR opens as a draft carrying the full verification report. The maintainer reviews, merges, or closes it. The agent never merges.

What makes it trustworthy

  • The maintainer is in the loop twice, non-negotiably: approve the winner before the agent runs, review the PR before anything merges.
  • Verification commands are discovered from the base commit before the agent runs and passed in — never re-discovered from the patched tree — so an agent cannot grade its own homework by rewriting the test script.
  • The secret scan resolves the runtime values of variables in the added lines (chains, joins, decoders, helper functions, branchy values) instead of matching known shapes.
  • Two audited maintainer escapes exist for honest blocks: retry-with-deps (dependency changes permitted for that run) and churn override.
This page is an explainer, not a live service. WishShip is a self-hostable web service (single service + Postgres via docker compose), not a hosted SaaS. Run it yourself from the repository.

Honest limits — stated, not hidden

  • docker compose up was never boot-verified in the development environment used for this build (no Docker there). Verify it on a machine with Docker before trusting a production deployment.
  • The real GitHub App push path has only ever run against the in-memory FakeGitHub client, never against a real repo. Verify it with a real GitHub App installation before trusting a production deployment.
  • The agent sandbox is worktree-level isolation plus environment hygiene — it is not a security boundary. PR review is the security boundary. Containerized runs are recommended.
  • The agent never merges, never holds a GitHub token, and never sees a secret. Stored service secrets are encrypted; the agent's environment is scrubbed of credential-shaped variables.
  • Diff-only secret scanning cannot resolve bindings from base code: a PR that adds only the second half of a secret whose first half is already committed is out of scope for the scanner by design.
  • Verification is deterministic but not omniscient: transform-aware obfuscation (custom ciphers, custom encodings, reorder tricks beyond array reverse) is undecidable for static analysis in general and is a documented residual — which is exactly why the maintainer reviews every draft PR.
